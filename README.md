# Mahmoud Hassan — Portfolio

A premium, dark-mode personal portfolio for **Mahmoud Hassan**, Front-End Developer and Computer Science student. The core site is plain **HTML5, CSS3, and vanilla JavaScript** — no frameworks, no build step — with two small, isolated full-stack additions:

- **`react-lab/`** — a real, isolated **React** feature (the "React Lab" section) rendering the same project data with its own component state.
- **`server/`** — a minimal **Node.js + Express** backend that the contact form actually talks to.

Neither replaces the existing architecture. Opening `index.html` (or serving the root with any static server) still shows the full, working portfolio exactly as before; the React Lab and backend are additive.

```
Existing Portfolio (HTML + CSS + Vanilla JS)
        |
        +---- react-lab/   → built into assets/react-lab/, mounted in #react-lab-root
        |
        +---- server/      → Express API for the contact form (POST /api/contact)
```

## Running the project

The static frontend needs no build tools or dependencies, same as before.

- **Frontend only (no contact form, no React Lab):** open `index.html` directly in a browser, or serve it:
  ```bash
  python3 -m http.server 8000
  ```
  Then visit `http://localhost:8000`. The contact form will honestly show its error state (backend not running) instead of faking success. `#react-lab-root` shows a small "not built yet" note instead of breaking.

- **Full stack (contact form + React Lab working):**
  ```bash
  # 1. Build the React Lab bundle once (rebuild after changing react-lab/src/)
  cd react-lab
  npm install
  npm run build

  # 2. Run the backend, which also serves the whole portfolio
  cd ../server
  npm install
  npm run dev
  ```
  Then visit `http://localhost:5000` — the full portfolio, React Lab, and a working contact form, all from one origin.

## Backend

A minimal Express API in `server/` backs the contact form — nothing more. No database, no auth, no admin panel.

- `POST /api/contact` — validates `name`, `email`, `subject`, `message` (all required, length-limited, email format checked), sends a real notification email via SMTP (Nodemailer), and only on successful delivery appends a timestamped entry to `server/data/messages.json`. Returns `201` on success, `400` with per-field errors on invalid input, `429` if the sender has submitted too many messages recently, `500` if email delivery fails or isn't configured.
- `GET /api/health` — returns `{ "status": "ok", "service": "Mahmoud Portfolio API", "emailConfigured": true|false }`. Never returns the API key or any other secret.
- Also serves the static portfolio itself (`express.static`), so the contact form's `fetch("/api/contact")` works same-origin with no extra configuration when you run the backend and open `http://localhost:5000`.
- CORS is scoped to an explicit allowed origin (via `ALLOWED_ORIGIN` in `.env`, default `http://127.0.0.1:5500`) for the case where you serve the frontend separately during development — never a wildcard.
- A hidden honeypot field (`website`) in the contact form catches simple bots: if it's filled, the API responds with a normal-looking success but skips both email delivery and persistence entirely.
- A lightweight in-memory rate limiter caps `POST /api/contact` at 5 submissions per IP per 10 minutes — scoped to that one route, not the rest of the site.

Run it:

```bash
cd server
npm install
cp .env.example .env   # then fill in the SMTP variables — see below
npm run dev
```

Messages persist to `server/data/messages.json`, which is gitignored (it can contain real visitor contact details).

## Contact Email Delivery

Real email delivery is handled by SMTP via [Nodemailer](https://nodemailer.com), in `server/services/emailService.js`.

```
Portfolio Form
      ↓
Express POST /api/contact
      ↓
Validation (+ honeypot + rate limit checks)
      ↓
Nodemailer → SMTP
      ↓
mahmoudalassiouty1@gmail.com
      ↓
Persist successful submission
```

The visitor's own email address is set as `replyTo` on the outgoing notification (never as `from`), so replying to the notification email goes straight back to the visitor. The `from` address itself is always `SMTP_USER` — most SMTP providers, Gmail included, reject sends where the `From` address doesn't match the authenticated account.

At startup, if SMTP is configured, the server calls `transporter.verify()` in the background and logs whether the connection is healthy — this never blocks startup or crashes the process, since a temporary SMTP outage shouldn't take the whole server down with it.

**If email delivery isn't configured or the SMTP server rejects the send, the API returns a `500` and the visitor sees a real error state — it never reports "Message sent" unless the email actually went out**, and nothing is written to `messages.json` in that case either.

### Setup

```bash
cd server
npm install
```

Create `server/.env` (copy `server/.env.example`) and fill in:

```env
PORT=5000
SMTP_HOST=smtp.gmail.com
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=your-email@gmail.com
SMTP_PASS=your_gmail_app_password
CONTACT_TO_EMAIL=your-email@gmail.com
CONTACT_FROM_NAME=Mahmoud Hassan
```

For Gmail, `SMTP_PASS` must be a **Gmail App Password**, not the normal account password — Google blocks plain-password SMTP login. Generate one at [myaccount.google.com/apppasswords](https://myaccount.google.com/apppasswords) (requires 2-Step Verification to be turned on first): App passwords → select "Mail" → generate → copy the 16-character password into `SMTP_PASS` (spaces don't matter, Nodemailer/Google accept it either way).

`server/.env.example` intentionally ships with placeholder values only, and `.env` itself stays out of git (see `.gitignore`).

No secrets are ever placed in frontend code (`index.html`, `js/script.js`, the React Lab bundle) — `SMTP_USER`/`SMTP_PASS` are read only in `server/services/emailService.js`, server-side.

## Contact form setup (Express backend)

The contact form posts to the Express API at `POST /api/contact` and shows honest sending/success/error states — it will **not** show "Message sent" unless the API actually returns success. To activate real delivery:

1. Follow the [Backend](#backend) steps above to install and run `server/`.
2. Open the portfolio through the backend itself, at `http://localhost:5000` (rather than a separate static server), so the form's request reaches the API on the same origin with no extra configuration.

Until the backend is running (or until `SMTP_USER` / `SMTP_PASS` are configured — see [Contact Email Delivery](#contact-email-delivery)), `js/script.js` correctly shows the error state ("Couldn't reach the server... contact me directly by email" or the generic delivery-failure message) instead of faking a success message. Submitted messages are stored in `server/data/messages.json` only after the notification email has actually been sent.

## Deployment

The static portfolio (including the built React Lab bundle) deploys exactly as before — GitHub Pages, Netlify, and Vercel all work with no build command, as long as `assets/react-lab/` has been built first (`cd react-lab && npm run build`) and committed or included in the deploy.

The Express backend in `server/` is a separate Node process and isn't served by any of these static hosts — deploy it to something that runs Node (Render, Railway, Fly.io, a small VPS, etc.), then update the `CONTACT_API_BASE` constant near the top of `initContactForm()` in `js/script.js` to point at that backend's real URL instead of `localhost:5000`. Without that step post-deploy, the contact form will correctly show its error state rather than pretending to send.

### GitHub Pages
1. Push this folder to a GitHub repository.
2. Go to **Settings → Pages**.
3. Under "Build and deployment", set **Source** to `Deploy from a branch`, choose the `main` branch and `/ (root)` folder.
4. Save — your site will be live at `https://your-username.github.io/repo-name/`.

### Netlify
1. Drag and drop the `portfolio` folder onto [app.netlify.com/drop](https://app.netlify.com/drop), **or**
2. Connect the GitHub repo in the Netlify dashboard and deploy with the default settings (no build command needed — it's a static site).

### Vercel
1. Import the GitHub repository at [vercel.com/new](https://vercel.com/new).
2. Framework preset: **Other**. No build command or output directory changes are needed.
3. Deploy.

After deploying, add real `og:url` and `<link rel="canonical">` tags in `index.html`'s `<head>` — they're currently omitted (not filled with a fake domain) with an HTML comment marking exactly where to add them once the real URL exists.

## Accessibility & performance notes

- Respects `prefers-reduced-motion` (disables the typing effect, particle canvas, and scroll animations).
- All interactive elements — including the mobile menu and the project details modal — are keyboard-reachable with visible focus states, trap focus while open, close on `Escape` and on backdrop click, and restore focus to the trigger element on close.
- Mobile menu locks background scroll while open and shows a backdrop overlay.
- Images use `alt` text; decorative elements use `aria-hidden`.
- Form fields use `aria-describedby` to link inputs to their error messages.
- The particle canvas: renders fewer particles on small screens, scales for `devicePixelRatio`, and pauses automatically when the hero section is off-screen or the browser tab is hidden — it never runs when it isn't visible.
- The particle canvas and floating orbs are purely decorative — the page is fully readable and usable with JavaScript disabled.
